# Library behavior and historical fidelity audit

The Library contains usable training machinery, but several cards promise entities, weapons or coaching that the generated mission does not supply. Keep the historical overlays; add dated provenance and distinguish reconstructed boundaries from illustrative training geometry. A successful `.miz` build must not be presented as content validation.

## Evidence and scope

Reviewed source revision `7c02868` on `codex/reliability-fixes`, descended from v1.106.0. Built **334 complete missions**, covering **111 entries** (108 JSON templates and 3 crew templates), **167 era/map variants**, and seeds **7 and 19**. All built successfully. Kept normal template flags, including ambient traffic and dressing. Inspected the emitted Lua mission tables, payloads, routes, groups, trigger rules, drawings, archive resources and generated statistics against card premises and briefing text.

`scripts/audit_library.py` reproduces the matrix. Evidence lives in `outputs/library-validation/` in the surrounding workspace: `case-summary.csv`, `template-review.csv`, `mission-evidence.json.gz`, and a small set of reproduction missions. The CSV's review status distinguishes confirmed mismatches from structural evidence with further verification pending. It does not award a pass merely because an entry builds.

Coverage includes each declared era and each explicit map whitelist; unrestricted cards use their effective default map. Alternative aircraft choices, arbitrary user overrides, every seed, deployed uploaded-pack revisions and DCS runtime behavior are outside this matrix. Installed pack data was isolated with `PACKS_DATA_DIR`; production pack bytes were unavailable. This is an evaluation of source-generated content, not certification of all files on the live server. No gameplay or historical data was changed by this audit.

The matrix uses the engine's fully merged effective recipe. The browser has a separate preset problem described below, so the matrix is not an end-to-end certification of the Library's Generate button.

## What has meaningful structural support

The AAR training entries emit a tanker with a real `Tanker` waypoint task. Coached rides and qualification variants emit trigger rules; operational-transfer rides intentionally omit grading. Formation entries supply a dedicated lead and exercise routes; the pre-check/check variants have distinct trigger sets. Timing lessons supply a route and grading triggers, with an extra flight for the package lesson. B'NAI coached variants emit their route and 39 trigger rules. Case III training stages emit stage-specific routes/triggers; final night CQ intentionally has no coaching triggers. Crew missions emit the dedicated intercept/raid/setup actors and trigger rules.

Those are evidence of implemented mechanics, not proof that their scoring, cues, AI behavior or refueling work in the current DCS build. Do not add a requirement for automated scoring to an explicitly ungraded exercise. `bc_cas1`, for example, honestly says there is no controller and asks the pilot to brief a self-directed 9-line. The generic two-seat ACM card also discloses its simplification. Preserve those disclosures.

## Historical boundaries and eras

The data contains **four overlay sets on four maps**: Germany, Nevada, Syria and Afghanistan. The other nine maps do not currently have authored historical-airspace overlays. Map `frontline_hint` text and selectable tactical air corridors are separate systems; they are not surveyed historical border polygons. Do not imply that every theater's tactical front or corridor is historically verified.

| Feature | Historical assessment | Required correction |
|---|---|---|
| Berlin corridors / BCZ | The three corridors, 20-statute-mile width, 20-mile BCZ radius and 10,000-foot ceiling are supported by the [1945 corridor agreement](https://history.state.gov/historicaldocuments/frus1945v03/d1199) and [BCZ flight rules](https://history.state.gov/historicaldocuments/frus1945v03/d1206). The code explicitly uses approximate terminals; the treaty defines the control-zone center at the Allied Control Authority building. | Retain as a **schematic historical overlay**, expose the approximation on the card/F10/kneeboard, and digitize a dated BASC chart before claiming exact alignment. Verify the separate 13,000-foot-exception claim before publishing it as a rule. The fighter transit card already discloses the real unarmed-transport versus DCS fighter substitution. |
| Nevada R-4808N | All 14 stored vertices match the legal boundary to the JSON's six-decimal rounding. However, the [FAA amendment, 60 FR 20625–20626](https://www.govinfo.gov/content/pkg/FR-1995-04-27/pdf/FR-1995-04-27.pdf), became effective **20 July 1995**. Data incorrectly cites page 20661 and applies that geometry to Cold War missions dated 1978. | Correct the citation and give the polygon a validity interval. Use the relevant earlier boundary for a historical 1978 mission, or disclose the modern DCS-map overlay. This verifies the 1995 transcription, not all subsequent amendments. |
| Euphrates deconfliction | The line was operationally real: a [February 2018 coalition account](https://www.defense.gov/News/News-Stories/Article/Article/1435258/syrian-pro-regime-forces-attack-prompts-coalition-defensive-strikes/) refers to the agreed line. The current four-point polyline is an approximation, and the generic modern mission date is 2011. The brief correctly distinguishes coordination from a sovereign border. | Require a dated scenario/line source; do not apply the later US/Russia arrangement to 2011. Label the geometry approximate. The cited account supports existence, not the exact four vertices. |
| Kabul TMA / Helmand ROZ | Helmand is already described as representative. No dated AIP/ACO in the repository authenticates the 30-statute-mile Kabul circle or the Helmand rectangle/vertical limits. A daily ROZ is not a timeless national boundary. | Retain as **illustrative training airspace** until a dated primary AIP/ACO is available. Record units, vertical limits, controlling agency and validity. Do not claim exact real-world boundaries. |

R-4808N also has a geometry implementation risk: `airspace.py` draws the polygon but exports a circumscribed **circular** trigger zone under the same `AIRSPACE R-4808N` name. That circle includes territory outside the published polygon. This audit found no demonstrated automatic penalty using it; nevertheless, future violation detection must use the polygon, not that zone as an exact boundary.

## Historical scenario integrity beyond the lines

`build_context.prepare_world()` assigns **21 June 1944, 1978, 2011 or 2016** from the era. There is no scenario date override. That is incompatible with map/lineup labels expressly naming **Sinai October 1973**, **Proud Phantom 1980** and **Falklands 1982**. Every generated Proud Phantom example in this matrix is dated 1978. The US Marine Corps' [history of US–Egypt relations](https://www.usmcu.edu/Portals/218/Boots%20and%20Suits.pdf) identifies the exercise in 1980. Keep its explicitly notional Libyan aggressor basing as an acknowledged DCS adaptation; fix its date rather than removing the exercise.

The Kola modern preset describes Norwegian/Finnish/Swedish **NATO** versus Russia while its default date is 2011. Finland and Sweden joined in [2023 and 2024 respectively](https://www.nato.int/cps/en/natohq/topics_49212.htm?selectedLocale=en). Either date that scenario from 2024 onward or label the alliance arrangement counterfactual. Likewise, the GWOT Afghanistan preset calls its 2016 setting OEF; [Army historical material](https://www.govinfo.gov/content/pkg/GOVPUB-D104-PURL-gpo219777/pdf/GOVPUB-D104-PURL-gpo219777.pdf) places OEF's conclusion in December 2014. Use the appropriate operation name/date.

Country assignment mixes territorial host and military operator. Caucasus Cold War bases are labeled Georgia even though the 1978 setting precedes [restored independence in 1991](https://ais.archive.gov.ge/en/sakartvelos-damoukideblobis-aghdgena-1). Parchim is assigned GDR while other Soviet-operated German bases use USSR; [Parchim's municipal planning report](https://www.parchim.de/de/ortsrecht/bau-und-stadtentwicklung/flaechennutzungsplaene/stadt-parchim/erlaeuterungsbericht-zum-flaechennutzungsplan-der-stadt-parchim.pdf?cid=4sv) records Soviet use from 1953 to 1992. Al Dhafra is assigned USA, whereas an [official USAF account](https://www.afcent.af.mil/Units/380th-Air-Expeditionary-Wing/News/Display/Article/3348817/cas-aircraft-arrive-in-middle-east/) identifies UAE hosts. Add separate host, operator, deployment and coalition fields, with date ranges. A US detachment does not make every parked aircraft at a UAE base American.

The F-100 Victor Alert card bases the aircraft at Bitburg in the generated year 1978. [Bitburg airport's own history](https://www.flugplatz-bitburg.de/infos/geschichte/geschichte.html) places its F-100 period in 1956–61, followed by F-105s and then F-4s. Describe an adaptation or provide the appropriate historical date/aircraft. The Falklands preset intentionally retains Mount Pleasant for playability; preserve the disclosure, but its note should distinguish construction from operational availability: the [RAF dates the station's opening to 1985](https://www.raf.mod.uk/our-organisation/stations/mount-pleasant-complex/).

Weapon service checks intersect an entire era window rather than the actual mission year (`loadouts.era_legal`). Consequently emitted 1978 F-4s carry AIM-7M missiles, which the [USAF dates to service entry in 1982](https://www.af.mil/About-Us/Fact-Sheets/Display/Article/104575/aim-7-sparrow/). Check exact scenario dates for historically strict missions. General DCS training can keep later equipment if the card explicitly says it uses available module variants. Parked-aircraft livery warnings also confirm that nationality-specific skin verification remains outstanding.

## Recommended implementation order

1. Fix C7's shared effective recipe and add browser-state regression cases. Otherwise engine-only content fixes can still be overridden by the Library flow.
2. Fix loadouts/equipment and missing central actors (C1–C4). Add actual archive assertions per card: required target, moving convoy, tanker task, strike weapons/action, recon pod, controlled intercept target and seat count.
3. Put a visible mode on every entry: **scenario**, **coached lesson**, **self-directed exercise** or **reference setup**. State what happens, what the pilot does, and what the mission measures. Preserve the Library's tracks and hierarchy, but ensure each card's premise agrees with its generated brief and mechanics.
4. Add scenario date plus historical classification: **reconstruction**, **historically inspired adaptation**, **fictional exercise**. Give each overlay a primary source, validity dates, geometry accuracy and vertical limits. Apply those dates to faction, airbase/operator, aircraft and weapon selection.
5. Flight-test representative mechanics in DCS: one boom/probe AAR check, formation check, timing/package lesson, B'NAI coach, each carrier stage, crew intercept/raid, and each repaired combat family. Record DCS/module versions and results; repeat only after relevant changes.

Existing `tests/test_library_promises.py` returned **80 passed, 33 skipped** despite the confirmed mismatches. It primarily examines `brief` text and a limited set of default builds, not the Library `premise`; some predicates use names or disclaimers rather than actual tasks. Keep its useful checks, but replace keyword heuristics with explicit per-card contracts. Run cheap metadata/contract tests in the routine suite and the complete generation matrix as a separate content-release check.
