# Contributing to DCS Mission Starter

Thanks for helping! The single most useful principle here: **the data packs are
the product, the code is plumbing.** Most improvements are JSON edits or exported
survey data — no engine changes — and those are the easiest PRs to review and
merge.

## Ways to contribute (easiest → deepest)

### 1. In-game validation reports (no code needed)
Generate a mission, fly it, and tell us what's wrong or right. Include:
- the **recipe + seed** (or the share-link code) so we can regenerate the exact mission,
- a **screenshot**, and what you expected vs. saw (a truck on a hangar, an
  aircraft facing the wrong way, a SAM in the sea, a livery that's off…).

Open it as an issue. This is genuinely as valuable as code — the generator can't
see in-game.

### 2. Data-pack additions (JSON only — the sweet spot)
All under `missiongen/data/`. Additive by design: a map/era/nation with no entry
falls back to a safe default, so you can't break existing missions.
- **`theater_identity.json`** — per-map/era *national ownership* of each airbase.
- **`nation_rosters.json`** — per-nation, era-gated fast-jet rosters (verified
  DCS module refs only).
- **`coastlines.json`** — schematic land/water outlines (lat/lon) for the Mission
  Brief chart. Water-heavy maps (Kola, Falklands, Marianas, Sinai) want these.
- **`historical_airspace.json`** — real corridors / no-fly zones / deconfliction
  lines (lat/lon), drawn on the F10 map + briefed.
- **`mission_templates.json`**, **`ramp_themes.json`** — scenario presets & ramp mixes.

Keep additions period-correct — the WWII data block is guarded against
anachronisms by `validate_data_packs` (fails `/api/health`).

### 3. Survey data (export from your own DCS install)
Some data can only come from the sim. `scripts/` builds throwaway `.miz` survey
missions you fly once; they log to `dcs.log`; an importer bakes the result:
- **Parking headings** — `build_survey_mission.py` → `import_survey.py` →
  `parking_headings.json` (exact static facing).
- **Scenery keep-out** — `build_scenery_survey.py` → `import_scenery.py` →
  `scenery_keepout.json` (buildings/hangars, so statics don't spawn on them).
- **DTC format** — `dtc_inspect.py` diffs a plain vs cartridge-configured mission.

You don't need Python installed to *fly* a survey — ask and we'll build the `.miz`
for you; you send back the `dcs.log`.

### 4. Engine / feature code
Python, `missiongen/`. Read the architecture in the README first. Two hard rules:
- **Never place player routing waypoints** — the north star is "we set the stage,
  you write the play." Reference geometry (airspace, bullseye, nav points) is fine.
- **Determinism is a contract** — the same recipe+seed must produce a
  byte-identical `.miz` (share links depend on it). Anything using randomness must
  key off the seeded `rng`. If your change alters generated bytes for an existing
  recipe, that's a MAJOR-version change; call it out.

## Dev setup

```
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
PYTHONPATH=vendor uvicorn server.app:app --reload   # http://127.0.0.1:8000
```
pydcs is vendored in `vendor/dcs` (no separate install needed).

## Before you open a PR

- Run the tests: `PYTHONPATH=vendor python3 tests/test_regressions.py` (and
  `tests/test_determinism.py`). CI runs these + the data-pack validator.
- If you added a data pack entry, generate a mission on that map/era and confirm
  it builds cleanly (`/api/health` should stay green).
- Add a `CHANGELOG.md` note and, for a released change, bump
  `missiongen/__version__`.
- Keep `vendor/dcs/` **unmodified** — pydcs behaviour changes go in
  `missiongen/_determinism.py` (runtime patch) or upstream to pydcs.
